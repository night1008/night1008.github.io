在日常技术研发中，很多工程师已经开始尝试用**多大模型协同**来写技术设计方案：

> 先让 **Gemini** 出一个方案初稿，方向很准、逻辑清晰，但总感觉缺了点底层落地的硬核细节；
> 于是转手把它丢给逻辑推演极强的 **DeepSeek** 做 Review：“帮我核实细节并补充完整”；
> 结果 DeepSeek “用力过猛”，不仅补了一堆极端边界，还顺带把“什么是幂等”、“Redis
为什么是内存数据库”、“建议打印规范日志”等大白话常识全塞了进去……
> 原本 3 页纸的轻量设计方案，瞬间膨胀成了一篇动辄万字、谁都不想看的“技术八股文”。

为什么两个各自领域顶尖的模型凑在一起，反而产生了一份“灾难级”的文档？我们又该如何驯服它们？

今天聊聊背后的机制原理，以及一套可以直接套用的**双模型高效协作流水线**。

---

## 一、 现象背后：两大模型的“人设冲突”

这个现象并非偶然，本质上是**发散创意型模型**与**严谨审查型模型**在认知策略上的碰撞。

```text
    Gemini (宏观架构师)                      DeepSeek (严苛审查官)
    ┌──────────────────┐		     ┌──────────────────┐
    │  擅长：顶层设计    │                   │  擅长：逻辑推演    │
    │  风格：抓大放小    │ ─── 方案初稿 ──>   │  风格：穷举完备    │
    │  盲点：缺乏细节    │                   │ 陷阱：防御性写作   │
    └──────────────────┘                  └──────────────────┘
                                                    │
                                                    ▼
                                            产出又臭又长的八股文
 ```

### 1. Gemini 的“默认信任”机制
Gemini 的宏观抽象能力很强，在生成设计方案时，它的默认假设是：**“读者是懂行的资深同行”**。
因此它会把重心放在业务架构、系统分层和选型理由上，而把基础异常处理、参数定义等实现细节省略掉。这导致文档看起来 **“方向极对，但有点发虚”**。

### 2. DeepSeek 的“防御性写作”陷阱
DeepSeek 等具备强推理（CoT）能力的模型，在收到 Review 指令时，触发的是 **“完备性优先”** 的底层逻辑。
* **没有读者画像**：由于不知道读者水平，模型会采用最保守的假设——默认读者可能会质疑任何细节。
* **防御性补偿**：在模型的世界里，“不写”等同于“疏漏”。为了证明自己考虑周全，它会开启“穷举教学”模式，把前置常识、底层原理连带最佳实践全部倒出来。
* **结果**：设计方案直接退化成了“技术百科全书摘录”。

## 二、 核心认知转变：Review 的输出是“原料”，不是“成品”

导致文档冗长的根本错误动作，是很多人习惯对 DeepSeek 说：**“请帮我完善细节，并重新生成一份完整方案。”**

这句话直接让模型接管了“编辑权”。大模型天然是做**加法**的，一旦放开篇幅，它绝不会主动克制。

> **核心认知：**
> **模型负责穷举，人类负责剪裁。Review 的产物应该是用来挑刺的“差分原料”，绝不能直接当作正文修订稿！**

---

## 三、 驯服模型的三条“手术刀法则”

要让两者的优势互补，我们需要在提问和协作机制上动手术：

### 法则 1：黄金红线 —— 区分“改变代码”与“解释原理”
筛选 Review 意见时，只用这一条硬标准做过滤：

* **保留（改变代码/架构）**：
  * *“主键如果用自增 ID，分库分表会产生碰撞，必须替换为雪花算法。”*（改变了数据结构，**必须留**）
  * *“下游网络抖动未做重试退避，容易雪崩，需增加指数退避重试。”*（改变了调用逻辑，**必须留**）
* **无情剔除（纯科普/空洞建议）**：
  * *“Redis 是内存型存储，发生宕机可能丢数据，需要持久化。”*（全人类都知道，**删**）
  * *“建议做好日志追踪，方便排查故障。”*（毫无意义的正确废话，**删**）

### 法则 2：让审查者“扮演具体反派”
不要让 DeepSeek 扮演泛泛的“资深架构师”，给它一个尖锐、刻薄的极窄人设，它的废话会骤减 90%：

> **推荐人设**：
> *“你是一个半夜被报警电话叫醒的 On-call 运维专家。假设这个系统明天上线且凌晨宕机了，请只指出 3 个最可能导致系统雪崩的致命硬伤。”*

身份越具象，模型的注意力就越集中在“故障与灾难边界”，没闲心再去科普常识。

### 法则 3：用结构本身抗冗余（ADR 格式）
要求模型在提出修改建议时，强制采用 **ADR（架构决策记录）** 的极简三元组：
* **面临约束**：一句话说明遇到了什么特殊场景。
* **所做决策**：选了什么技术/改了哪个字段。
* **代价权衡**：牺牲了什么，引入了什么副作用。

凡是写不出这个三元组的建议，一律判定为“常识水文”，直接丢弃。

## 四、 最佳工程实践：三步走协同 SOP

下面这套流程，已被大量技术团队验证为信噪比最高的大模型协作姿势：

```
Gemini (起草骨架) ──> 结构化初稿
                          │
                          ▼
DeepSeek (靶向挑刺) ──> 缺陷与盲区 Checklist (绝不碰正文)
                          │
                          ▼
人类工程师 (人工裁决) ──> 用“改变代码法则”筛选出 2~3 个真问题 ──> 定点回填定稿
```

### Step 1：Gemini 出骨架（用契约逼出细节）
让 Gemini 起草时，不要给纯概念提示词，直接索要“具体交付物”：

```markdown
请帮我设计 [业务需求] 的技术方案：
1. 给出整体架构图与核心时序图（Mermaid 格式）。
2. 给出核心数据库表的 DDL 定义，包含字段与索引。
3. 给出核心 API 的 Request/Response Schema。
4. 读者均为熟练工程师，无需解释原理，重在逻辑闭环。
```

### Step 2：DeepSeek 做刺客（只挑刺，不出正文）
拿到初稿后，把正文喂给 DeepSeek，加上严格的负面约束：

```markdown
你是资深系统架构师，读者均为拥有 5 年以上经验的后端开发，请对以下方案做技术评审：

【严格约束】
1. 默认读者掌握全部开发常识（如常见中间件原理、幂等概念、常规日志与监控规范），严禁输出任何科普性与套话内容。
2. 严禁重写文档正文！

【输出格式】
以极简清单列出你的意见：
- 致命缺陷：是否存在状态不一致、死锁或并发竞争？
- 缺失契约：漏掉了哪些关键字段、状态码或回滚逻辑？
只列出“如果不修改会导致线上 BUG”的问题，每条不超过 3 句话。
```

### Step 3：人工裁决，定点缝合
* 浏览 DeepSeek 返回的 Checklist；
* 大手一挥，删掉那些“提醒你加日志”、“解释原理”的条目；
* 把真正有价值的 2~3 个极端边界，手工或让 Gemini 定点补充到方案的 **《边界考量与异常兜底》** 章节中。

## 结语

大模型时代的写方案，不再是 **“谁能敲出更多字”** 的竞赛，而是 **“如何维持极高信息密度”** 的博弈。

* **Gemini 是望远镜**，帮你看清星空与路线；
* **DeepSeek 是显微镜**，帮你排查暗礁与裂痕；
* **而你，必须是手握剪刀的主编**。

别指望一个模型同时做好发散、审查与精简三件事；学会解耦它们的分工，你才能真正拥有一支不知疲倦、各司其职的高级架构师智囊团。
